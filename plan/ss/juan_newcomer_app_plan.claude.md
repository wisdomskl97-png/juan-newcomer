# 주안 새가족 등록앱 기획안 (Claude 작성)

## 0. 왜 이 문서를 새로 쓰는가

`juan_newcomer_app_plan.md`(기존 버전)와 별개로, 사용자가 전달한 원본 요구사항을 처음부터 다시 분석해서 작성한 버전입니다. 구조와 우선순위, 특히 **대학목장 데이터 격리 문제**에 대한 접근 방식이 기존 버전과 다릅니다.

## 1. 문제 정의부터

지금 프로세스의 진짜 문제는 "등록이 종이라서 느리다"가 아니라, 다음 두 가지입니다.

1. **이중 입력(paper → Google Form)** 때문에 팀원의 노동이 두 번 든다.
2. **대학목장 대상자가 일반 새가족 DB에 섞여 들어갈 수 있는 구조적 위험**이 있다. 지금은 "말로 먼저 물어보고" 종이를 다르게 처리하는 방식인데, 이건 사람이 실수하기 쉬운 지점이다 (바빠서 깜빡하고 구글폼에 그냥 입력해버림).

→ 이 앱의 존재 이유는 **속도**보다 **분류 정확성**이어야 합니다. 이 관점이 아래 모든 설계 결정의 기준입니다.

## 2. 앱 이름

| 후보 | 용도 | 코멘트 |
|---|---|---|
| **주안 웰컴 (JUAN Welcome)** | 새가족이 보는 화면 이름 | 부담 없고 친근함, 영문 병기 자연스러움 |
| 주안 새가족 등록 | 팀 내부 호칭 / 관리 시트 이름 | 기능을 그대로 설명 |
| 새가족카드 | 대안 | "카드 한 장 작성한다"는 느낌, 짧음 |

**추천**: 새가족 앞에는 "주안 웰컴", 팀 내부 문서·코드 저장소명은 "juan-newcomer" 그대로 사용.

## 3. 등록 플로우 — 분류를 첫 화면 최상단에 고정

기존 방식은 "말로 물어보고 → 종이로 분리"였는데, 앱에서는 이 질문을 **소프트웨어 로직으로 강제**해야 실수가 없어집니다.

```
[QR 스캔]
   ↓
[화면 1: 목장 분류 질문] ← 반드시 첫 화면, 건너뛸 수 없음
   "학생비자 이거나, 시드니에서 대학 재학/입학 예정이신가요?"
   [예] → 대학목장 경로       [아니오] → 일반목장 경로
   ↓                            ↓
[화면 2-A: 대학목장 안내]     [화면 2-B: 일반 새가족 등록폼]
   - DB에 저장하지 않음          - 전체 항목 입력
   - 대학팀 연락처만 안내         - 제출 → DB 저장
   - (선택) 이름/연락처만         ↓
     별도 시트에 임시 기록      [화면 3: 완료 메시지]
     → 대학팀이 직접 컨택
```

**핵심 설계 포인트**: 대학목장 경로는 아예 등록 폼 컴포넌트 자체를 로드하지 않습니다. "같은 폼에 입력 후 필터링해서 안 보이게" 방식이 아니라, **분기 시점에 다른 코드 경로로 완전히 분리**하는 게 맞습니다. 이래야 "실수로 구글폼에 입력되는" 지금의 사고 패턴이 애초에 발생할 수 없습니다.

### 대학목장 로그 (`UniversityLeads`) — 선택 사항

이름 + 연락처 + 시각만 기록하는 **최소 로그**. 목적은 "대학팀에 제대로 인계됐는지 확인"용이며, 새가족 상세정보는 담지 않음. 이렇게 하면:
- 종이 인계가 누락돼도 최소한 "누가 왔었는지"는 추적 가능
- 그러면서도 상세 개인정보(비자, 세례여부 등)는 아예 시스템에 안 들어감

## 5. 잘못 저장된 대학목장 데이터 처리

요청하신 "실수로 구글폼에 입력되면 지워야 한다"는 요구사항 — 이건 **사후 삭제 절차가 필요 없도록 사전에 막는 게 최우선**이지만, 그래도 사람이 관리 화면에서 직접 잘못 등록된 항목을 지우는 경우를 대비해:

- 관리자 화면에 `group_type = 일반목장`인 항목만 노출 (혹시 잘못 들어간 대학목장 항목이 있다면 별도 "검토 필요" 필터로 표시)
- "삭제" 액션은 소프트 삭제(deleted_at 플래그)로 처리 — 실수로 지운 걸 복구 가능하게
- Google Sheets 기반이면 삭제 로그를 별도 시트에 남기는 Apps Script 훅 추가 (누가 언제 지웠는지)

## 6. Google Sheets vs Notion — 실제 트레이드오프

| 기준 | Google Sheets | Notion |
|---|---|---|
| Apps Script로 폼 제출 연동 | 매우 쉬움 (fetch → doPost) | API 연동 필요, 인증 토큰 관리 필요 |
| 팀원 학습 곡선 | 이미 씀, 0 | 새로 배워야 함 |
| 담당자별 뷰/칸반 (연락상태 관리) | 약함, 필터/피벗 필요 | 강함, DB뷰 기본 지원 |
| 검색/필터 UX | 보통 | 좋음 |
| 모바일에서 팀원이 확인하기 | 앱은 있으나 불편 | 앱 UX 우수 |
| 자동화(알림 등) 확장성 | Apps Script로 가능하지만 손이 감 | Notion API + Zapier/Make 연동 쉬움 |
| 비용 | 무료 | 무료(개인)~유료(팀 협업 시) |

**제 추천은 기존 문서와 동일하게 1차는 Sheets, 안정화 후 Notion**이지만, 이유를 좀 더 구체화하면: 지금 당장 필요한 건 "제출 → 저장"이라는 단순 파이프인데 여기엔 Notion의 강점(뷰, 관계형 DB)이 크게 필요하지 않습니다. 반면 Notion의 강점은 "담당자 배정 → 후속 연락 추적 → 정착 상태 관리"라는 **운영 단계**에서 발휘되므로, 등록 파이프라인이 안정된 후 옮기는 게 낭비가 적습니다.

단, **바로 Notion으로 가는 것도 나쁜 선택은 아닙니다** — 웹훅 방식(Make.com/Zapier 무료 티어, 또는 HTML 폼 → Notion API 직접 호출)으로 초기부터 갈 수도 있고, 이후 데이터 마이그레이션이 없다는 장점이 있습니다. 제가 원 문서와 다르게 강조하고 싶은 점은: **팀원 중 Notion을 이미 익숙하게 쓰는 사람이 있는지가 결정 기준의 8할**이라는 것입니다. 기술적 난이도보다 사람 문제입니다.

## 7. 새가족 UX에서 놓치기 쉬운 디테일

원 문서에 없던, 실제 현장 등록 시나리오에서 자주 발생하는 문제들:

- **와이파이/데이터 문제**: 교회 실내에서 QR 스캔 후 데이터가 안 터지는 경우 대비 — 폼을 최대한 가볍게(이미지 최소화), 오프라인 우선 저장 후 온라인 복귀 시 자동 재전송(localStorage 큐) 고려
- **한 폰으로 여러 명 등록**: 가족 단위로 온 경우 한 사람 폰으로 여러 명 등록 → 제출 후 "한 명 더 등록하기" 버튼 필요
- **다음 주에도 같은 사람이 다시 스캔**: 중복 제출 방지 — 연락처 기준 "이미 등록된 번호입니다" 안내 (덮어쓸지, 새 레코드로 할지는 팀 정책 필요)
- **손글씨보다 느릴 수 있음**: 특히 어르신 새가족은 폰 입력이 종이보다 느릴 수 있음 → "팀원이 대신 입력" 모드(같은 폼, 등록경로만 다르게 기록)는 계속 남겨둬야 함
- **개인정보 동의 문구**: 호주 Privacy Act 기준 최소한의 동의 문구 필요 (수집 목적, 보관 기간, 담당자 명시)

## 8. 관리자 쪽 기능 우선순위 (MoSCoW)

**Must have (MVP)**
- 목장 자동 분류 및 저장 분리
- 새가족 목록 확인 (날짜순)
- CSV/시트 다운로드
- 개인정보 동의 로그

**Should have (2차)**
- 담당자 배정, 후속연락 상태 관리
- 중복 연락처 감지 및 경고
- 팀원 알림 (신규 등록 시 슬랙/카톡 알림)

**Could have (3차)**
- Notion 연동 또는 완전 전환
- 주간 자동 리포트
- 대학목장 인계 확인 대시보드

**Won't have (지금은 제외)**
- 로그인 기반 관리자 권한 시스템 (초기엔 링크 자체를 비공개로 공유하는 걸로 충분)
- 새가족 자동 메시지 발송 (카카오톡 API는 심사/비용 이슈가 있어 초기 범위 밖)

## 9. 기술 스택 제안

- **Frontend**: 순수 HTML/CSS/JS (프레임워크 없이) — 배포 단순성과 유지보수 용이성 우선, 팀원이 나중에 코드를 봐야 할 수도 있으니 복잡한 빌드 체인 피함
- **QR 생성**: 정적 URL 하나면 되므로 무료 QR 생성기(예: qrcode.js 라이브러리로 페이지 내 생성, 또는 외부 생성 후 인쇄)
- **저장소**: Google Apps Script Web App (doPost) → Sheets (1차)
- **배포**: GitHub Pages (무료, 정적 호스팅에 적합, HTTPS 자동 지원 — QR 스캔 시 카메라 접근에 HTTPS 필수)
- **버전 관리**: Git 저장소로 관리 — 지금 프로젝트 폴더가 아직 git repo가 아니므로, 개발 시작 전에 `git init` 권장
