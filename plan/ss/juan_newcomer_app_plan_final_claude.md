# 주안 새가족 등록앱 기획안 (Final)

> `juan_newcomer_app_plan.md`(1차 버전)와 `juan_newcomer_app_plan.claude.md`(재작성 버전)를 비교·통합한 최종 기획안입니다.

## 1. 프로젝트 개요

### 목적

시드니 주안교회에 매주 방문하는 새가족들이 QR 코드를 통해 직접 정보를 입력하고, 새가족팀이 이를 효율적으로 관리할 수 있는 등록·관리 앱을 만든다.

### 현재 문제

지금은 종이 등록 → 팀원이 Google Form에 재입력 → Google Sheets 저장 순서로 진행된다. 이 방식의 진짜 문제는 두 가지다.

1. **이중 입력**: 종이 → 폼 재입력으로 팀원 노동이 두 배 든다.
2. **대학목장 데이터 혼입 위험**: 지금은 "말로 먼저 물어보고" 종이를 다르게 처리하는 방식이라, 담당자가 바빠서 깜빡하고 구글폼에 그대로 입력해버리면 대학목장 대상자 정보가 일반 새가족 DB에 섞여 들어갈 수 있다.

→ 이 앱의 존재 이유는 **속도**보다 **분류 정확성**이다. 이 관점이 아래 모든 설계 결정의 기준이 된다.

## 2. 앱 이름

| 후보 | 용도 | 코멘트 |
|---|---|---|
| **주안 웰컴 (JUAN Welcome)** | 새가족이 보는 화면 이름 | 부담 없고 친근함, 영문 병기 자연스러움 |
| 주안 새가족 등록 | 팀 내부 호칭 / 시트·문서 이름 | 기능을 그대로 설명, 관리용으로 적합 |
| 주안 새가족 카드 | 대안 | "카드 한 장 작성한다"는 느낌 |

**최종 추천**: 새가족용 화면 이름은 **"주안 웰컴"**, 내부 관리·코드 저장소명은 **"주안 새가족 등록"(juan-newcomer)**으로 이원화한다.

## 3. 현재 등록 방식 (As-Is)

1. 새가족이 교회에 방문한다.
2. 팀원이 종이 등록지를 전달한다.
3. 새가족이 종이에 정보를 작성한다.
4. 팀원이 해당 정보를 Google Form에 입력한다.
5. Google Form 응답이 Google Sheets에 저장된다.

### 현재 수집 항목

이름/Name, 연락처/Contact, 인도자/Introducer, 비자종류(워킹홀리데이/영주권/시민권/여행/학생/기타), 전공·직업/Job, 생년월일/DOB, 세례여부/Baptism status, 이전 출석 교회, 이전 봉사 부서, 카카오톡 아이디.

## 4. 핵심 운영 조건 — 목장 분류

시드니 주안교회는 새가족을 **일반목장**과 **대학목장** 두 갈래로 관리한다. 지금은 새가족을 만났을 때 먼저 말로 아래를 확인한다.

- 학생비자인지
- 시드니에서 대학 재학 중인지
- 시드니에서 대학 입학 예정인지

해당되면 대학목장 대상자로 분류하고, 종이로 정보를 받아 대학팀에 직접 전달한다. **이 정보는 일반 새가족 데이터베이스에 저장되면 안 된다.**

## 5. 등록 플로우

분류 질문을 앱의 **첫 화면 최상단, 건너뛸 수 없는 단계**로 고정한다. "같은 폼에 입력받고 나중에 필터링"하는 방식이 아니라, **분기 시점에 코드 경로 자체를 분리**해서 대학목장 선택 시 일반 등록 폼 컴포넌트가 아예 로드되지 않도록 한다. 이래야 "실수로 구글폼에 그대로 입력되는" 지금의 사고 패턴이 구조적으로 발생할 수 없다.

```
[QR 스캔]
   ↓
[화면 1] 목장 분류 질문 (필수, 스킵 불가)
   "학생비자 이거나, 시드니에서 대학 재학/입학 예정이신가요?"
   ↓ 예                          ↓ 아니오
[화면 2-A] 대학목장 안내       [화면 2-B] 일반 새가족 등록폼
   - 일반 DB에 저장 안 함         - 전체 항목 입력
   - 대학팀 연락처 안내           - 개인정보 동의
   - (선택) 이름+연락처만          - 제출 → DB 저장
     최소 로그로 기록            ↓
     → 대학팀 인계 확인용      [화면 3] 제출 완료 화면
```

### 대학목장 최소 로그 (선택 기능)

이름+연락처+시각만 기록하는 별도 로그(`UniversityLeads`). 목적은 "종이 인계가 실제로 이뤄졌는지" 추적용이며, 비자·세례여부 등 상세 개인정보는 담지 않는다. 종이 인계가 누락돼도 최소한 "누가 왔었는지"는 확인 가능하면서, 민감 정보는 시스템에 들어가지 않는 균형점이다.

## 7. 잘못 저장된 대학목장 데이터 처리 절차

1순위는 **애초에 못 들어가게 구조적으로 막는 것**(5번 참고)이지만, 관리자가 실수로 잘못 등록하는 경우를 대비한 절차:

- 삭제는 하드 삭제가 아닌 **소프트 삭제**(`deleted_at` 플래그)로 처리해 실수 복구 가능하게 한다.
- 삭제 시 누가/언제 지웠는지 별도 로그 시트에 기록한다 (Apps Script 훅).
- 관리자 화면은 기본적으로 `group_type = 일반목장`만 노출하고, 혹시 잘못 들어간 항목은 "검토 필요" 필터로 별도 표시한다.

## 8. 데이터베이스: Google Sheets vs Notion

| 기준 | Google Sheets | Notion |
|---|---|---|
| Apps Script/API로 폼 제출 연동 | 매우 쉬움 (doPost) | API 연동 및 토큰 관리 필요 |
| 팀원 학습 곡선 | 이미 사용 중, 0 | 새로 배워야 함 |
| 담당자별 뷰·연락상태 관리 | 약함 (필터/피벗 필요) | 강함 (DB 뷰 기본 지원) |
| 모바일에서 팀원이 확인 | 다소 불편 | 우수 |
| 자동화(알림 등) 확장성 | Apps Script로 가능하나 손이 감 | API + Make/Zapier 연동 쉬움 |
| 비용 | 무료 | 무료(개인)~유료(팀 협업 시) |

**최종 추천**: 1차 MVP는 **Google Sheets**로 시작하고, 운영이 안정된 후 **Notion으로 전환**을 검토한다.

이유:
- 지금 당장 필요한 건 "제출 → 저장"이라는 단순 파이프라인이고, 여기엔 Notion의 강점(관계형 뷰)이 크게 필요하지 않다.
- Notion의 강점은 "담당자 배정 → 후속 연락 추적 → 정착 상태 관리"라는 **운영 단계**에서 발휘되므로, 등록 파이프라인이 안정된 뒤 옮기는 편이 마이그레이션 낭비가 적다.
- 다만 **결정 기준의 상당 부분은 기술이 아니라 사람**이다 — 새가족팀 중 Notion에 이미 익숙한 팀원이 있다면 처음부터 Notion으로 가는 것도 합리적인 선택이다. 이 경우 웹훅(Make.com/Zapier 무료 티어 또는 Notion API 직접 호출)으로 초기부터 연동 가능하고, 이후 데이터 마이그레이션이 없다는 장점이 있다.

## 9. 새가족 UX — 현장에서 실제로 터지는 문제들

- **와이파이/데이터 문제**: 교회 실내에서 QR 스캔 후 연결이 불안정할 수 있다. 폼을 최대한 가볍게 만들고, 필요하면 localStorage에 임시 저장 후 온라인 복귀 시 재전송하는 방식을 고려한다.
- **가족 단위 등록**: 한 사람 폰으로 여러 명을 등록하는 경우가 많다 — 제출 후 "한 명 더 등록하기" 버튼 필요.
- **중복 제출 방지**: 연락처 기준으로 이미 등록된 번호면 안내 문구를 띄운다. 덮어쓸지 새 레코드로 남길지는 팀 정책으로 확정 필요.
- **팀원 대신 입력 모드**: 어르신 등 폰 입력이 어려운 새가족을 위해, 같은 폼을 팀원이 대신 입력하는 경로를 남겨둔다 (`registration_source = 팀원입력`으로 구분).
- **개인정보 동의 문구**: 호주 Privacy Act 기준 최소 동의 문구 필요 (수집 목적, 보관 기간, 담당자 명시).

## 10. 필요 기능 — 우선순위(MoSCoW)

**Must have (MVP)**
- 목장 분류 질문 및 분기 (코드 경로 완전 분리)
- 일반목장 대상자 정보 Google Sheets 저장
- 대학목장 대상자 안내 화면 (DB 미저장)
- 개인정보 수집 동의 체크
- 모바일 최적화, 한국어/영어 병기
- QR 코드 접속
- 제출 완료 화면

**Should have (2차)**
- 새 등록자 목록 확인, 날짜별 필터
- 담당자 배정, 후속연락 상태 관리
- 중복 연락처 감지
- CSV 다운로드
- 팀원 알림 기능 (신규 등록 시)

**Could have (3차)**
- Notion 연동 또는 전환
- 주간 자동 리포트
- 대학목장 인계 확인 대시보드
- 관리자 로그인

**Won't have (지금은 제외)**
- 로그인 기반 관리자 권한 시스템 (초기엔 비공개 링크 공유로 충분)
- 카카오톡 자동 메시지 발송 (API 심사·비용 이슈로 초기 범위 밖)
- Notion 양방향 실시간 동기화

## 11. 기술 스택

- **Frontend**: 순수 HTML/CSS/JS — 프레임워크 없이, 배포 단순성과 팀원의 유지보수 용이성 우선
- **QR 생성**: 정적 URL 기반, 페이지 내 QR 생성 라이브러리(qrcode.js) 또는 외부 생성 후 인쇄
- **저장소(1차)**: Google Apps Script Web App(doPost) → Google Sheets
- **배포**: GitHub Pages (무료, HTTPS 자동 지원 — QR 스캔 후 폼 접속에 HTTPS 권장)
- **버전 관리**: 현재 프로젝트 폴더가 git 저장소가 아니므로, 개발 착수 전 `git init` 권장

## 12. 필요 화면 (디자인 단계 대상)

1. QR 접속 첫 화면
2. 목장 분류 질문 화면

4. 대학목장 안내 화면
