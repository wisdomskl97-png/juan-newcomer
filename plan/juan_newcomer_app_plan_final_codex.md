# 주안 새가족 등록앱 최종 기획안

## 0. 문서 목적

이 문서는 `juan_newcomer_app_plan.md`와 `juan_newcomer_app_plan.claude.md` 두 기획서를 비교한 뒤, 실제 개발에 사용할 최종 방향을 정리한 문서이다.

최종안의 기준은 다음과 같다.

- 새가족이 QR 코드를 통해 직접 쉽게 등록할 수 있어야 한다.
- 팀원의 종이 등록지 입력 업무를 줄여야 한다.
- 일반목장과 대학목장 대상자를 앱 초반에 정확히 분류해야 한다.
- 대학목장 대상자가 일반 새가족 데이터베이스에 저장되는 일을 구조적으로 막아야 한다.
- 첫 버전은 HTML/CSS/JavaScript 기반의 가벼운 MVP로 시작한다.

## 2. 최종 앱 이름

### 새가족이 보는 이름

**주안 웰컴 / JUAN Welcome**

이름이 부담스럽지 않고, QR로 처음 접속하는 새가족에게 자연스럽다. 한국어와 영어 병기도 쉽다.

### 팀 내부 관리 이름

**주안 새가족 등록**

기능이 명확하고, 내부 문서, Google Sheets, Notion, 관리자 화면 이름으로 사용하기 좋다.

### 프로젝트 폴더/코드 이름

**juan-newcomer**

현재 프로젝트 이름과도 잘 맞고, 개발용 이름으로 간결하다.

## 3. 문제 정의

현재 새가족 등록 방식의 핵심 문제는 단순히 종이를 사용한다는 점이 아니다. 실제 문제는 다음 두 가지이다.

1. 새가족이 종이에 작성한 정보를 팀원이 다시 Google Form에 입력해야 한다.
2. 대학목장 대상자가 실수로 일반 새가족 데이터베이스에 저장될 수 있다.

따라서 이 앱의 핵심 목적은 단순한 디지털 폼 제작이 아니라, **새가족 등록 흐름을 단순화하고 목장 분류 실수를 구조적으로 방지하는 것**이다.

## 4. 핵심 운영 원칙

시드니 주안교회는 새가족을 크게 두 흐름으로 관리한다.

- 일반목장
- 대학목장

대학목장 대상자는 일반 새가족 데이터베이스에 저장되지 않아야 한다. 앱은 이 원칙을 사람이 기억해서 지키는 방식이 아니라, 시스템 흐름으로 강제해야 한다.

### 대학목장 분류 기준

아래 조건에 해당하면 대학목장 대상자로 분류한다.

- 학생비자 소지자
- 시드니에서 대학 재학 중인 사람
- 시드니에서 대학 입학 예정인 사람

## 5. 최종 등록 플로우

```text
[QR 코드 스캔]
        |
        v
[목장 분류 질문 화면]
학생비자이거나, 시드니에서 대학 재학/입학 예정이신가요?
        |
        +-- 예 --> [대학목장 안내 화면]
        |           - 일반 새가족 DB 저장 안 함
        |           - 대학목장용 정보 입력
        |           - 대학팀 공유용 요약 생성
        |           - 카카오톡/이메일/복사로 대학팀 전달
        |           - 선택적으로 별도 인계 저장소에만 저장
        |
        +-- 아니오 --> [일반 새가족 등록 폼]
                    - 전체 정보 입력
                    - 개인정보 수집 동의
                    - 제출
                    - 등록일 자동 기록
                    - Google Sheets 저장
                    - 완료 화면
```

### 중요한 설계 결정

대학목장 대상자는 일반 새가족 등록 폼으로 이동하지 않는다. 같은 폼에서 입력받은 뒤 나중에 필터링하는 방식이 아니라, 첫 질문 이후 아예 다른 화면과 다른 데이터 흐름으로 분리한다.

이렇게 해야 대학목장 대상자가 일반 새가족 데이터베이스에 저장되는 사고를 가장 확실하게 줄일 수 있다.

단, 대학목장 대상자도 대학팀 인계를 위해 필요한 정보는 받을 수 있다. 이 경우 일반 새가족 데이터베이스에는 저장하지 않고, 제출 직후 공유용 메시지를 생성하거나 별도 대학목장 인계 저장소로만 보낸다.

## 6. 화면 구성

### 1. QR 접속 첫 화면

목적:

- 새가족이 교회 등록 화면에 잘 들어왔음을 확인한다.
- 너무 많은 설명 없이 바로 다음 단계로 이동하게 한다.

주요 요소:

- 주안 웰컴 / JUAN Welcome
- 간단한 환영 문구
- 시작하기 버튼

### 2. 목장 분류 질문 화면

목적:

- 일반목장과 대학목장 흐름을 가장 먼저 나눈다.

질문:

> 현재 학생비자이거나, 시드니에서 대학 재학 또는 입학 예정이신가요?

선택지:

- 예
- 아니오

이 화면은 건너뛸 수 없게 만든다.

### 3. 일반목장 새가족 등록 폼

목적:

- 일반목장 대상자의 새가족 정보를 수집한다.

방향:

- 모바일 우선
- 한국어와 영어 병기
- 필수 항목은 최소화
- 입력 부담을 줄이기 위해 섹션을 나눈다.

### 4. 대학목장 안내 화면

목적:

- 대학목장 대상자를 대학팀 흐름으로 안내한다.
- 일반 새가족 DB 저장을 방지한다.
- 대학팀이 바로 연락할 수 있도록 필요한 정보를 전달한다.

주요 요소:

- 대학목장 안내 문구
- 대학팀 담당자 연락처
- 대학팀 별도 등록 링크가 있다면 버튼 제공
- 대학목장용 정보 입력 폼
- 제출 후 카카오톡/이메일/복사용 공유 메시지 생성

### 4-1. 당일 요약 화면

목적:

- 그날 등록된 새가족 명단을 팀원이 빠르게 확인하고 공유할 수 있게 한다.

표시 정보:

- 이름
- 태어난 해
- 등록 구분
  - 일반목장
  - 대학목장

주요 기능:

- 오늘 등록자 목록 보기
- 복사하기
- 공유하기
- 이메일로 보내기

요약 예시:

```text
2026-08-15 주안 새가족 등록 요약

[일반목장]
- 김주안 (1998년생)
- John Lee (2001년생)

[대학목장]
- 박시드니 (2004년생)
```

주의할 점:

- 요약에는 이름과 태어난 해만 표시한다.
- 연락처, 생년월일 전체, 비자 정보, 세례 여부 등 상세 개인정보는 요약에 포함하지 않는다.

### 5. 제출 완료 화면

목적:

- 등록이 정상적으로 완료되었음을 알려준다.

주요 요소:

- 감사 메시지
- “한 명 더 등록하기” 버튼
- 필요 시 교회 연락처 또는 예배 안내

### 6. 관리자 확인 화면

MVP에서는 별도 관리자 화면을 만들지 않고 Google Sheets를 관리 화면처럼 사용한다. 2차 개발에서 관리자 페이지를 추가한다.

## 7. 데이터베이스 최종 추천

### 최종 추천

**1차 MVP는 Google Sheets로 시작하고, 운영이 안정된 후 Notion 연동 또는 전환을 검토한다.**

### Google Sheets를 먼저 추천하는 이유

- 현재 Google Form과 Google Sheets를 이미 사용 중이다.
- 팀원이 새 도구를 배울 필요가 적다.
- HTML 앱과 Google Apps Script 연동이 비교적 단순하다.
- MVP를 빠르게 만들 수 있다.
- 초기에는 Google Sheets 자체가 관리자 화면 역할을 할 수 있다.

### Notion을 나중에 검토하는 이유

Notion은 단순 저장보다 관리 단계에서 강점이 있다.

- 담당자별 보기
- 후속 연락 상태 관리
- 카드형 새가족 관리
- 메모와 히스토리 관리
- 주간 관리 뷰 구성

다만 팀원들이 Notion에 익숙하지 않다면 운영 부담이 커질 수 있다. Notion 도입 여부는 기술 난이도보다 팀의 사용 습관을 기준으로 결정하는 것이 좋다.

### 날짜 저장 기준

`submitted_at`은 정확한 제출 시각을 저장하고, `registration_date`는 운영상 “등록한 날짜”를 저장한다.

예:

- `submitted_at`: `2026-08-15 11:23:45`
- `registration_date`: `2026-08-15`

날짜는 교회가 위치한 시드니 현지 날짜 기준으로 기록한다. Google Apps Script에서 서버 시간대를 `Australia/Sydney`로 맞추거나, 프론트엔드에서 전송한 날짜를 Apps Script에서 다시 검증해 저장한다.

### 대학목장 인계 데이터: `UniversityHandoff`

대학목장 대상자는 일반 새가족 DB에 저장하지 않는 것이 원칙이다. 다만 대학팀 인계를 위해 같은 정보를 받을 수 있다.

이 데이터 처리 방식은 세 가지 옵션이 있다.

### 옵션 A: 저장하지 않고 공유만 하기

대학목장 대상자가 정보를 입력하면 앱이 공유용 메시지를 만든다. 팀원은 이 메시지를 복사하거나 카카오톡/이메일로 대학팀에 전달한다. 앱은 해당 정보를 일반 DB에 저장하지 않는다.

장점:

- 일반 새가족 DB 혼입 위험이 가장 낮다.
- 구현이 단순하다.
- 개인정보 저장 부담이 적다.

단점:

- 팀원이 공유 버튼을 누르지 않으면 인계 기록이 남지 않는다.
- 나중에 누락 여부를 확인하기 어렵다.

### 옵션 B: 별도 대학목장 인계 시트에 저장하기

대학목장 정보는 일반 `Newcomers` 시트가 아니라 별도 `UniversityHandoff` 시트에만 저장한다.

장점:

- 대학팀 인계 누락을 확인할 수 있다.
- 당일 대학목장 요약 목록을 만들기 쉽다.
- 일반 새가족 DB와 분리된다.

단점:

- “DB에 저장하지 않는다”는 원칙을 엄격하게 해석하면 맞지 않을 수 있다.
- 접근 권한과 보관 기간을 별도로 정해야 한다.

### 옵션 C: 이메일 자동 발송 후 저장하지 않기

대학목장 정보 제출 시 Google Apps Script가 대학팀 이메일로 내용을 보내고, 시트에는 저장하지 않는다.

장점:

- 팀원이 직접 공유하지 않아도 된다.
- 일반 새가족 DB에 저장되지 않는다.
- 대학팀이 바로 확인할 수 있다.

단점:

- 이메일 누락, 스팸, 수신 확인 문제가 있을 수 있다.
- 카카오톡으로 바로 보내는 것보다 현장성이 떨어질 수 있다.

### 최종 추천

MVP에서는 **옵션 A + 복사/공유 기능**으로 시작한다. 동시에 2차 개발에서 **옵션 C: 대학팀 이메일 자동 발송**을 추가하는 것을 추천한다.

대학팀이 인계 누락을 자주 겪는다면 옵션 B를 도입하되, 이 시트는 일반 새가족 DB와 분리하고 접근 권한을 대학팀과 담당자에게만 제한한다.

### 대학목장 입력 항목

대학목장 대상자도 일반 새가족과 같은 기본 정보를 받을 수 있다. 단, 저장 위치와 공유 방식은 일반목장과 분리한다.

| 필드명 | 타입 | 필수 여부 | 설명 |
|---|---|---|---|
| submitted_at | datetime | 자동 | 제출 시간 |
| registration_date | date | 자동 | 앱에 정보를 입력한 날짜 |
| name | text | 필수 | 이름 / Name |
| contact | phone | 필수 | 연락처 / Contact |
| kakao_id | text | 선택 | 카카오톡 아이디 |
| birth_year | number | 선택 | 태어난 해. 요약 공유용 |
| date_of_birth | date | 선택 | 생년월일. 공유 메시지 포함 여부는 별도 결정 |
| introducer | text | 선택 | 인도자 |
| visa_type | select | 필수 | 학생, 워킹홀리데이, 기타 등 |
| job_or_major | text | 선택 | 전공 또는 직업 |
| baptism_status | select | 선택 | 세례 여부 |
| previous_church | text | 선택 | 이전 출석 교회 |
| previous_activity | text | 선택 | 이전 봉사 부서 |
| privacy_consent | boolean | 필수 | 대학팀 인계를 위한 개인정보 공유 동의 |

주의할 점:

- 대학목장 정보는 일반 `Newcomers` DB에 저장하지 않는다.
- 공유 메시지에는 필요한 정보만 포함한다.
- 당일 요약에는 이름과 태어난 해만 표시한다.
- 대학팀이 별도 등록 시스템을 갖고 있다면 이 정보는 그 시스템으로 전달하는 방식도 가능하다.

## 8-1. 당일 요약 및 공유 기능

### 목적

주일 또는 행사 당일에 등록된 새가족 목록을 팀원이 빠르게 확인하고, 이름과 태어난 해만 포함한 요약을 복사하거나 공유할 수 있게 한다.

### 요약 범위

- 오늘 등록된 일반목장 새가족
- 오늘 대학목장으로 분류되어 인계된 사람

### 요약에 포함할 정보

- 이름
- 태어난 해
- 등록 구분

포함하지 않을 정보:

- 연락처
- 카카오톡 ID
- 생년월일 전체
- 비자 정보
- 세례 여부
- 이전 교회
- 메모

### 구현 옵션

#### 옵션 1: Google Sheets 기준 요약

일반목장 데이터는 `registration_date = 오늘`인 행을 기준으로 요약한다. 대학목장 데이터는 저장하지 않는 MVP에서는 포함하기 어렵고, 별도 `UniversityHandoff` 시트를 사용할 때만 자동 포함할 수 있다.

#### 옵션 2: 브라우저 임시 저장 기준 요약

그날 같은 기기에서 입력한 일반목장/대학목장 정보를 브라우저 `localStorage`에 임시로 저장하고, 당일 요약 화면에서 보여준다.

장점:

- 대학목장 정보를 일반 DB에 저장하지 않아도 당일 요약에 포함할 수 있다.
- 구현이 빠르다.

단점:

- 다른 기기에서 입력한 사람은 한 화면에 합쳐 보이지 않는다.
- 브라우저 데이터를 지우면 요약이 사라질 수 있다.

#### 옵션 3: 별도 요약 시트 사용

상세 정보는 저장하지 않고, 이름과 태어난 해, 등록 구분, 등록일만 별도 `DailySummary` 시트에 저장한다.

장점:

- 여러 기기에서 등록해도 당일 요약을 한 번에 볼 수 있다.
- 상세 개인정보를 저장하지 않는다.
- 복사/공유 기능을 안정적으로 만들 수 있다.

단점:

- 최소한의 데이터라도 별도 저장이 발생한다.
- 보관 기간과 접근 권한을 정해야 한다.

### 최종 추천

MVP에서는 **옵션 3: 별도 요약 시트 사용**을 추천한다.

이유:

- 여러 팀원이 각자 다른 기기로 등록해도 당일 리스트를 하나로 볼 수 있다.
- 요약에는 이름과 태어난 해만 저장하므로 개인정보 노출을 줄일 수 있다.
- 일반목장/대학목장 모두 같은 요약 방식으로 처리할 수 있다.
- 마지막에 복사하거나 공유하기 기능을 안정적으로 만들 수 있다.

`DailySummary` 시트 구조:

| 필드명 | 타입 | 설명 |
|---|---|---|
| registration_date | date | 등록일 |
| group_type | select | 일반목장 또는 대학목장 |
| name | text | 이름 |
| birth_year | number | 태어난 해 |
| created_at | datetime | 요약 생성 시각 |

### 공유 방식

- 복사하기: 요약 텍스트를 클립보드에 복사한다.
- 공유하기: 모바일 Web Share API를 사용해 카카오톡, 메시지, 이메일 등 사용 가능한 앱으로 공유한다.
- 이메일 보내기: `mailto:` 링크 또는 Apps Script 이메일 발송을 사용한다.

카카오톡으로 바로 특정 채팅방에 자동 전송하는 기능은 초기 범위에서 제외한다. 카카오톡 API는 설정, 심사, 비용, 권한 문제가 있을 수 있으므로 MVP에서는 Web Share API 또는 복사 기능으로 처리한다.

## 15. 최종 권장 MVP

최종 MVP는 다음 범위로 만든다.

1. 새가족이 QR로 접속한다.
2. 첫 화면에서 대학목장 대상 여부를 확인한다.
3. 대학목장 대상자는 일반 등록 폼으로 가지 않고 대학팀 안내 화면으로 이동한다.
4. 대학목장 대상자는 대학팀 인계를 위한 정보를 입력한다.
5. 대학목장 정보는 일반 새가족 DB에 저장하지 않고 공유용 메시지와 당일 요약에만 사용한다.
6. 일반목장 대상자는 등록 폼을 작성한다.
7. 일반목장 데이터는 등록일과 함께 Google Sheets에 저장한다.
8. 제출 후 완료 화면을 보여준다.
9. 마지막에 그날 받은 명단 요약을 이름과 태어난 해만 포함해 복사하거나 공유할 수 있다.

이 범위가 첫 버전으로 가장 적절하다. 이유는 빠르게 만들 수 있고, 현재 운영의 가장 큰 문제인 이중 입력과 대학목장 데이터 혼입 문제를 동시에 줄일 수 있기 때문이다.

## 15-1. 확정 사항 (2026-08-15)

1단계 최종 결정 항목 중 아래 세 가지를 확정한다.

- **앱 이름**: 새가족용/내부용을 나누지 않고 **"주안 새가족등록"** 하나로 통일한다.
- **대학목장 인계 방식**: **옵션 A (저장 없이 공유만)**로 MVP를 시작한다. 대학목장 대상자 정보는 일반 `Newcomers` DB는 물론 별도 시트에도 저장하지 않고, 제출 직후 공유용 메시지만 생성해 팀원이 복사/카카오톡/이메일로 대학팀에 전달한다.
- **당일 요약(DailySummary) 기능**: MVP에 **포함**한다. 8-1절의 옵션 3(별도 요약 시트, 이름+태어난 해만 저장) 방식을 채택한다.
- **디자인 방향**: 클로드(Claude)의 디자인 기능을 활용하고, 시드니 주안교회 로고(`image/juanlogo.png`)를 앱 디자인에 반영한다. 상세 디자인 브리프는 `plan/juan_newcomer_app_design_prompt.md` 참고.

남은 결정 항목(대학목장 필수 입력 항목 범위, Google Sheets 컬럼 최종 확정)은 디자인 단계와 병행해 정리한다.

## 15-2. 결정 번복 (2026-08-16)

백엔드 연동 이후 실사용 중 "팀 요약 화면에서 대학목장 등록자도 상세정보를 볼 수 있어야 한다"는 필요가 확인되어, 15-1의 **"대학목장 인계 방식: 옵션 A" 결정을 폐기**했다. 대학목장도 일반목장과 동일하게 `Newcomers`에 전체 정보를 `group_type = 대학목장`으로 저장하도록 변경했다 (`backend/apps_script.gs`, `docs/script.js` 참고). 개인정보 최소화 원칙은 이 시점부터 대학목장에는 더 이상 적용되지 않는다.
