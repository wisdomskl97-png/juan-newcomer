# 주안 새가족등록 프로토타입 리뷰

> 대상 파일: `design/prototype/주안 새가족등록.dc.html` (읽기 전용 리뷰, 앱 파일은 수정하지 않음)
> 비교 기준: `plan/juan_newcomer_app_plan_final_codex.md` (확정 기획안, 특히 "15-1. 확정 사항")

## 총평

전체적으로 브랜드 톤(색감·타이포), 모바일 우선 레이아웃, 한/영 병기, 목장 분류 강제 분기, 당일 요약의 이름+태어난해만 노출하는 개인정보 최소화 원칙은 기획안과 잘 맞게 구현되어 있습니다.

다만 **핵심 원칙 두 가지가 실제 데이터 흐름(코드) 레벨에서는 기획과 어긋나 있습니다** — ① 개인정보 동의 체크박스가 화면에 없음, ② "대학목장은 저장하지 않고 공유만 한다(옵션 A)"는 원칙과 달리 대학목장 상세정보가 실제로는 저장·편집 가능한 구조로 되어 있습니다. 이 두 가지는 지금 단계(프로토타입)에서는 큰 문제가 아니지만, 이 화면 그대로 실제 개발(Apps Script 연동)로 넘어가면 원칙이 깨진 채 구현될 위험이 있어 우선적으로 짚습니다.

---

## 1. [High] 개인정보 수집·이용 동의 체크박스가 화면에 없음

- 기획안 5, 9, 11절 모두 "개인정보 수집 및 이용 동의"를 **Must-have 필수 항목**으로 명시했고, 디자인 프롬프트에도 "하단에 개인정보 수집·이용 동의 체크박스(필수)"라고 명확히 요청했습니다.
- 코드 상 `form.consent`, `handlers.consent` 상태는 존재하지만, 일반목장 폼(3번 화면)과 대학목장 폼(4번 화면) 어디에도 **체크박스 UI가 렌더링되어 있지 않습니다.**
- `validateGeneral()` / `validateUniv()` 함수도 `consent` 값을 검사하지 않아, 지금 로직대로면 동의 없이도 제출이 완료됩니다.
- **제안**: 두 폼 제출 버튼 위에 동의 체크박스 + 동의 문구 요약 + "자세히 보기"를 추가하고, `validate*()`에 `if (!f.consent) er.consent = '개인정보 수집·이용에 동의해주세요'`를 넣어야 합니다. (기획안 9절에 동의 문구 초안이 이미 있습니다.)

## 2. [High] 대학목장 데이터가 "저장하지 않고 공유만" 원칙과 다르게 동작함

- 확정 사항(final_codex.md 15-1절): **"옵션 A(저장 없이 공유만)"**로 MVP 시작. 대학목장 정보는 일반 DB는 물론 어디에도 저장하지 않고, 제출 즉시 공유용 메시지만 만든다는 원칙입니다.
- 실제 코드(`submitUniv()`)는 이름/연락처/카카오/생년월일/비자/전공/인도자/세례여부/이전교회/이전봉사부서를 포함한 전체 정보를 `this.state.today` 배열에 `flow:'univ'`로 그대로 push합니다. 이는 일반목장 등록자와 **동일한 리스트, 동일한 데이터 구조**에 저장되는 것입니다.
- 그 결과:
  - 팀 요약 화면에서 해당 등록자를 탭하면 "수정" 시트가 열리고, 연락처·비자·전공 등 상세정보가 그대로 노출·수정됩니다. (요약 리스트 자체는 이름+태어난해만 보여줘서 원칙을 지키는 것처럼 보이지만, 한 번의 탭으로 전체 정보가 열립니다.)
  - "대학목장 전달 메시지 만들기" 버튼도 즉시 생성되는 게 아니라, 나중에 팀 요약 화면에서 그날 쌓인 `today` 리스트를 다시 훑어 메시지를 조립하는 방식입니다. 즉 정보가 어딘가에 "쌓여 있어야" 메시지를 만들 수 있는 구조입니다.
  - 대학목장 안내/입력 화면 어디에도 "이 정보는 저장되지 않으며 대학팀 전달용으로만 사용됩니다"라는 디자인 프롬프트에 명시했던 문구가 없습니다.
- 지금은 프로토타입이라 실제 백엔드 저장이 아니라 브라우저 메모리(React state)일 뿐이지만, **이 구조를 그대로 Apps Script에 연결하면 일반 폼과 똑같이 대학목장 정보도 시트에 저장되는 코드가 나올 가능성이 큽니다.** 애초에 "코드 경로를 완전히 분리"하자는 기획 의도(final_codex.md 5절)와 다르게, 지금 프로토타입은 두 흐름이 같은 데이터 모델로 합류되어 있습니다.
- **제안**: 실제 개발 단계에서 일반목장 제출과 대학목장 제출이 서로 다른 함수/엔드포인트로 가도록 명확히 분리하고, 대학목장 제출 시에는 (a) 제출 직후 공유 메시지를 바로 보여주고, (b) 팀 요약용으로는 이름+태어난해만 별도로 저장(옵션 3, DailySummary)하고, (c) 연락처 등 상세정보는 그 세션에서만 쓰고 어디에도 지속 저장하지 않는 방식으로 재설계가 필요합니다.

## 3. [Medium] 일반목장 폼에서 생년월일이 필수(*) 항목으로 되어있음

- `validateGeneral()`에 `if (!f.birth) er.birth = ...`로 생년월일이 필수입니다.
- 기획안 데이터 스키마(final_codex.md 8절)에서는 `date_of_birth`가 **선택** 항목입니다. (당일요약에 "태어난 해"를 쓰긴 하지만, 요약 원본 기획도 필수로 강제하진 않았습니다.)
- 새가족이 처음 만난 자리에서 생년월일까지 필수로 요구하면 심리적 부담이 늘 수 있습니다. 의도된 변경이면 괜찮지만, 확인이 필요합니다.

## 4. [Medium] 대학목장 완료 화면에 공유 메시지 미리보기가 없음

- 디자인 프롬프트 5번 화면 스펙: "(대학목장의 경우) 생성된 공유 메시지 미리보기 박스 + 복사하기/공유하기 버튼"을 **제출 완료 화면에** 요청했습니다.
- 실제 구현은 제출 완료 화면(`isCompleteUniv`)에는 감사 메시지만 있고, 공유 메시지 생성·복사는 팀 요약 화면 안의 별도 팝업(`showUnivMsg`)으로 옮겨져 있습니다. 게다가 이 메시지는 그날 등록된 대학목장 대상자 전원을 모아 한 번에 만드는 "일괄 메시지"로 바뀌어 있습니다.
- 개인별 인계가 아니라 일괄 인계 방식으로 바뀐 것은 나쁘지 않은 아이디어(누락 방지에는 오히려 유리)지만, 새가족 본인이 자기 정보가 어떻게 전달되는지 볼 수 없다는 점에서 최초 요청과는 다른 설계입니다. 의도적 변경인지 확인이 필요합니다.

## 5. [Medium] 등록 삭제가 소프트 삭제가 아니라 하드 삭제

- 기획안 7절: "삭제는 하드 삭제가 아닌 소프트 삭제(`deleted_at` 플래그)로 처리해 실수 복구 가능하게 한다. 삭제 시 누가/언제 지웠는지 로그를 남긴다."
- 프로토타입의 `deleteCurrent()`는 배열에서 항목을 완전히 제거(`filter`)할 뿐, 복구나 로그 개념이 없습니다. 확인 팝업("삭제할까요? 되돌릴 수 없습니다")은 있지만, 이는 되돌릴 수 없다는 것을 명시적으로 인정하는 것이라 오히려 기획 원칙과 반대입니다.
- 지금은 프로토타입(메모리 데이터)이라 문제가 없지만, 실제 백엔드 연동 시 소프트 삭제 방식으로 바뀌어야 합니다.

## 6. [Low / 참고] 기획에 없던 기능이 다수 추가됨

프로토타입이 원 기획(MVP Must-have)보다 더 나아간 기능들을 포함하고 있습니다. 완성도는 높지만, MVP 범위를 넘어서는지 팀 논의가 필요합니다.

- **팀 PIN 잠금**: 요약 화면 진입 시 4자리 PIN 요구. 좋은 아이디어지만 기본값이 코드에 `'1234'`로 하드코딩되어 있어 실제 배포 시 반드시 변경/환경변수화 필요.
- **지난 기록(아카이브) 조회**: 월/주 단위로 과거 등록 내역을 탐색하는 기능. 기획안에는 "당일 요약"만 Must-have였고, 이력 조회는 계획에 없었습니다 (2차/3차 관리자 대시보드 영역에 가까움).
- **인라인 수정/삭제**: 요약 화면에서 등록자 정보를 직접 수정·목장 재분류까지 가능. 편리하지만 기획엔 없던 "관리자 기능"이 미리 들어간 형태입니다.

이 기능들 자체는 나쁘지 않고 오히려 실무에 유용해 보이지만, "MVP는 최대한 가볍게"라는 기획 원칙(final_codex.md 13절 "제외" 항목: 관리자 대시보드 등)과는 범위가 어긋나므로, 이번 스프린트에 다 가져갈지 별도로 결정하는 게 좋겠습니다.

## 7. [Low / 참고] `registration_source`(등록경로: QR / 팀원입력) 구분이 없음

- 기획 스키마에는 새가족이 직접 QR로 등록했는지, 팀원이 대신 입력했는지 구분하는 필드가 있었습니다. 프로토타입에는 이 구분을 위한 화면/토글이 없습니다. 실제로는 "팀원이 새가족 대신 같은 폼을 작성"하는 시나리오로 충분히 커버되긴 하지만, 데이터에 출처가 안 남는 점은 개발 단계에서 챙겨야 합니다.

## 잘 반영된 부분 (긍정적으로 확인된 항목)

- 목장 분류 질문이 첫 화면 다음에 오고, "홈으로" 외에는 건너뛸 방법이 없어 강제 분기 원칙을 잘 지킴.
- 일반목장/대학목장 폼 필드 구성이 기획 스키마와 거의 1:1로 일치 (이름/연락처/카카오/생년월일/인도자/비자/전공/세례/이전교회/이전봉사부서).
- 한국어/영어 병기가 라벨 전반에 일관되게 적용됨.
- 당일 요약 리스트 자체는 이름+태어난해+목장배지만 노출 — 개인정보 최소화 의도가 리스트 단위에서는 지켜짐 (단, 2번 항목에서 지적했듯 탭하면 뚫림).
- 일반목장(인디고)과 대학목장(오렌지)의 색 구분이 명확해 두 흐름이 헷갈리지 않음.
- "한 명 더 등록하기" 버튼으로 가족 단위 연속 등록 시나리오를 지원.
- 카카오톡 ID 찾는 법 도움말 팝업 등, 실제 새가족 입장에서 필요한 디테일까지 챙김.
